# 自建校验脚本的写法坑(prompt 常量 / 判据 vs 工件)

复验委派交付时,主代理常会**现写一个校验脚本**(或子代理为自己写)。这类"临时校验器"自身很容易出三类错,代价是返工、超时、甚至橡皮图章式放行。下面是实测记录。

## 1. prompt 里给的常量是"当时快照",不是事实

任务 prompt 会写诸如"582 key / 20 个文件 / 3 个接口"这类数字。它只代表**写 prompt 那一刻**的仓库状态。并行子代理、开发者、上游提交都可能在你干活期间改动源文件。

实测:整档翻译任务里 prompt 说 582 key,翻译期间源文件被插入 3 个新 key → 585。**只信 prompt 就会少交付 3 条**,而且所有"按 prompt 数字断言"的检查都会绿。

做法:
- 复验时**当场从源文件重新推导**计数/集合/顺序,再与目标比对;prompt 里的数字只用来**交叉核对**(不一致就是漂移信号,要去查而不是去改目标)。
- 漂移检查:源 mtime vs 目标 mtime;`comm` 双向集合差列出**具体缺哪些/多哪些**(列名字,不是只报个数)。
- 判定漂移性质(tracked 源文件用 git):`git diff` 只有 `+` 行 = 纯新增 → 既有译文仍有效,只补新条目;出现 `-` 行 = 改写 → 相关条目译文要重审。

## 2. FAIL 先怀疑判据,再怀疑工件

自建校验第一次报 FAIL 时,先重新推导"正确的不变量是什么",确认判据没写错,再去动工件。

实测两个 FAIL **全是判据错**:
1. 品牌/标识符白名单漏了 `Face ID`(Apple 韩文系统本来就不翻译它)→ 判据把**正确的**译文判成漏翻。
2. 把"我没改这类源文件"误写成"源文件与 HEAD 无 diff"→ 上游刚加过键,判据必然红;正确不变量是"源 diff 只含纯新增,且新键已出现在目标中"。

做法:改判据后**显式说明哪些 FAIL 属判据错**;不要把阈值悄悄放宽以求全绿——那是橡皮图章,等于没验。反之,若 FAIL 是真工件缺陷,也不要为了"跑通"而降低标准。

## 3. 生成/运行脚本本身的速死坑

- **生成"脚本里的脚本"**:外壳字符串用 `r'''...'''`。非 raw 时内层 `f"...\n..."` 的 `\n` 会被外壳吃成真换行 → 内层 `SyntaxError: unterminated f-string literal`。
- **先编译再执行**:`py_compile.compile(path, doraise=True)` 毫秒级抓语法错,别等一整轮执行/超时才暴露。
- **不留空转循环**:手滑的 `while <cond>: pass` 会把执行卡到超时(实测 300s),超时还会留下临时脚本残骸;下一轮先 `glob` 清理再跑。
- 临时脚本用 `tempfile.mkstemp(prefix="hermes-verify-", dir=<$TMPDIR>)`,跑完 `os.unlink`,别把校验器留进仓库。

### 3b. bash 校验脚本:三个静默致命的写法(实测,一次会话里踩了两回)

- **`UID` 是 bash 只读变量,别拿它当自己的变量名**:`UID=$(...)` 会打印 `readonly variable` 并**静默保留 shell 自身的 uid(501)**,后续比较/拼接全部用错值(表现为「明明注册成功却全程 401」)。同类只读/特殊变量还有 `EUID`、`PPID`、`RANDOM`、`SECONDS`、`LINENO`。**用 `TUID`/`ACCT_ID` 这类名字**。判断信号:输出里出现 `readonly variable`,或某变量值像 501/其他系统数字。
- **脚本退出码 = 系统的判定结果,别让收尾语句决定它**:复验脚本常以清理语句结尾,一旦那句返回非零(实测 `rm -f "$D" -r` 的 `-r` 位置写错 → `rm` 报错),**整轮被记为 FAILED,尽管 16 项检查全打印 PASS**,还要重跑一遍才能拿到干净判定。做法:收尾前显式 `[ "$FAIL" -eq 0 ] || exit 1` + `exit 0`,`trap cleanup EXIT` 里只放清理、并给可能失败的清理加 `|| true`;也别把验证脚本和 `; echo EXIT=$?` 之类的语句链在一起跑。
- **远端/子命令别吞 stderr、别省掉上传断言**:`out=$(ssh host 'cmd 2>/dev/null')` 这种写法在「辅助脚本其实没上传成功」时只会得到**空字符串**,而你看到的是莫名其妙的空输出(实测:换用临时目录当 scp 源后该段变空,加了 `if ! scp …; then bad "上传失败"; fi` 后立刻能定位)。做法:先断言传输成功再执行,并保留 stderr(`2>&1`)让原因可见。


## 4. 汇报纪律

交付汇报里区分三类,别混成一句"全部通过":
- 真工件缺陷(改了什么、怎么验的)
- 判据自身缺陷(哪个检查写错了、改成什么不变量)
- 上游环境变化(prompt 常量过时/源文件漂移)
并注明哪些检查是"ad-hoc 自建脚本"(仓库无 canonical 测试/lint 时),不要把它说成"测试套件全绿"。
