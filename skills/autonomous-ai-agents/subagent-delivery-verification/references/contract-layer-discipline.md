# 共享契约层(API 封装文件)的纪律 — 实测 2026-10 某聊天App Android 端

## 场景

规格文件驱动的并行代码生成中,主会话常落盘一份**共享契约层**(如 `api-ext.ts`:新端点封装、类型定义),供所有子代理引用。本文件的教训:**契约层本身是主会话的产物,同样会写错,且错误会被所有子代理继承**。

## 实测错案(两处,均在 `api-ext.ts`)

1. **转发端点字段名猜错**:契约写 `{targetRoomId, msgId, iv, cipher, ...}`,服务端 `/chat/rooms/:id/forward` 实际读 `{sourceMsgId, srcRoomId, cipher, iv, kind, meta, ts}`(`:id` 就是目标房间,调用方须同时是源/目标房间成员,目标 seq 由服务端计算)。
2. **收藏列表响应键猜错**:契约写 `{items: [...cipher]}`,服务端 `GET /chat/starred` 实际返回 `{ok, starred: [{msgId, roomId, seq, ts, kind, metaEnc, iv}]}`,且**故意不含 cipher**(正文必须按 `roomId+seq` 走房间 history 接口取,再本地解密)。

## 做对的部分(值得保留的做法)

- **子代理没有默默绕过**:两个子代理在最终汇报里都如实标注"字段与服务端不匹配"(契约错配清单),没有按错误契约把业务代码改"对"。这验证了规格里写"契约层只读,错配要上报"是有用的 —— **契约文件要显式声明自己是只读锚点,并要求子代理把错配写进阻塞清单**。
- **修复路径正确**:修的是**契约层**(`api-ext.ts`)+ 直接消费方,然后补协议级端到端验证(真实服务端:收藏→按 history 取文→解密、转发→目标房间解密出与原消息一致的明文、非成员 403)。类型检查通过 ≠ 服务端认账。
- **并行写不互踩的前提**:契约层、壳(MobileApp/样式/原生桥)、共享 CSS 锚点全部由主会话 own;子代理只写自己目录下的功能屏;并发自检命令用 `tsc --noEmit`(不写产物),避免多代理抢 `dist/` 与 tsbuildinfo。

## 可操作规则(以后写共享契约层时)

1. 每个字段名/响应键**对着服务端路由源码 grep 一遍**再落盘,不凭路由名猜(尤其"服务端故意不返回某字段"这类设计,如收藏不含 cipher)。
2. 契约文件头部注释写明:本文件为只读锚点、由主会话维护、子代理发现错配**不要自己改**,写进汇报的阻塞清单。
3. 子代理回传错配时:主会话先核服务端源码确认谁对,再改契约层;改完必须补**协议级端到端验证**(对真实服务端,覆盖正/负向断言),不能只跑类型检查。
4. 验证脚本(判定性断言轮)**前台执行**并留下可见输出 —— 放后台跑 PASS 了也不算登记在案的验证证据(证据登记会报 expired,且引用旧输出)。长耗时部分(构建)可后台 + notify,最后断言轮前台收口。
